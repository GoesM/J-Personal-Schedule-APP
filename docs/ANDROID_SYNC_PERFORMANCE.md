# 安卓拉取更新性能建议（2026-10-23）

实施更新：1.5.0 已实现阶段计时、无变化远端快速路径、批量历史读取、同步内 Git 缓存，以及仅在检出改变 HEAD 后重载。详见 `release/1.5.0同步加速.md`。本地脏文件清单与历史增量缓存尚未启用：当前仍检查实际工作区，有更新时批量完整读取，以保留异常恢复和旧数据兼容保障。

本次依据代码检查，未连接真机、未采集用户网络或仓库耗时，因此下列是已确认的开销路径及待测优先级，不是实测耗时占比。

## 当前路径

`src/sync.mjs` 的启动拉取虽然不 push，仍先 add 全部 ops/longtodo，再 statusMatrix，必要时 commit，然后 listServerRefs、fetch、merge、checkout、load。远端没有变化时也会执行这些扫描和重载。启动入口已经 load 一次，同步结束再 load 一次。

`src/store.mjs` 的 load 会依次读取每一个日程/单日 TODO 历史操作 JSON。编辑越多，文件越多；长期 TODO 虽已按工作集和月份归档，Git 扫描仍覆盖仓库文件。

Android MainActivity 将文件调用放入单线程队列，每次读取经过 Java → Base64 → evaluateJavascript → JS 解码。Git 的大量 stat/read/list 调用会反复跨越 WebView 桥。HTTP 数据也整包缓存并以 Base64 传输（编码体积约增加三分之一）。当前 Git 调用未共享 cache。

因此优先怀疑“小文件数量 × 跨桥调用次数”和无变更路径的重复工作，再测网络与远端服务延迟。不能简单归因于 Git 不适合安卓。

## 建议顺序

1. 先增加本机耗时统计：分别记录本地扫描/提交、远端查询、fetch、merge、checkout、重载的毫秒数，以及桥调用次数和读写字节数。记录首同步、无变化、单条远端修改、多端并发四种场景，至少比较同一网络下 Windows 与安卓；日志不得包含令牌、事项正文或凭据 URL。
2. 优化无变化路径：记录本地脏文件清单、同步成功状态和已应用的远端 OID。确认工作区干净且远端 OID 未变化时直接结束；本地有改动仍先安全保存/提交。冷启动、异常退出或标记不可信时回退完整检查，不能仅凭缓存跳过用户改动。
3. 批量和增量读取：原生提供批量目录元数据及操作读取；每次只解析新增操作，远端有变化才刷新对应内容。给一次同步中的 isomorphic-git 调用共享 cache，并在切换仓库或外部变更时失效。共享缓存单独衡量收益，不能假设会消除所有跨桥开销。
4. 历史增长治理：为日程/单日 TODO 加快照与分段归档，保留因果关系、删除墓碑和冲突版本；先做旧版兼容与断电恢复设计。不能直接删 Git 历史或把所有操作合并成一个不断增长的大 JSON。
5. 若上述仍慢，再评估将安卓 Git 执行移至原生层（如 JGit），避免逐文件桥接，仅将进度和结果返回界面。这涉及鉴权、合并、仓库兼容和回归成本，应独立验证原型后决定，不宜作为第一步。

交互上建议显示具体阶段与进度，避免长时间只显示“同步中”。可将后台拉取与安全应用更新分开设计，但不能在工作区变更时允许无约束并发写入。

推荐下一轮先做第 1–3 项；以无变化拉取和单条远端修改的真机 P50/P95 耗时、桥调用数、网络字节数作为验收指标，同时维持离线修改、双端冲突、失败重试和数据完整性测试。具体目标在基线测量后设定，本次不承诺未经测量的加速倍数。
